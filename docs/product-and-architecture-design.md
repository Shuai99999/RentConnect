# RentConnect 产品与技术设计说明

> 文档状态：草案 v0.1  
> 最后更新：2026-10-14  
> 适用范围：RentConnect MVP 及后续迭代  
> 维护原则：业务规则发生变化时，先更新本文档，再修改模型、数据库和测试。

## 1. 文档目的

RentConnect 是一个连接房东、租户和同住室友的租住协作平台。它不只是房源展示网站，还需要处理租期中的协作事项，例如：

- 租户向房东提交报修；
- 房东、报修人和同住室友跟踪处理进度；
- 围绕房屋或报修事项沟通并保留记录；
- 记录水、电、燃气、网络等共享账单；
- 按清晰、可追溯的规则计算每位室友应承担的金额；
- 在保护隐私的同时，让有权参与的人看到一致的信息。

本文档定义产品边界、核心概念、业务规则、权限、主要流程、数据设计、测试策略和云端部署方向。它是后续编码和评审的共同参考，但不是不可修改的最终合同。

## 2. 产品目标与非目标

### 2.1 产品目标

1. 为房东和租户提供围绕真实租住关系的可信协作空间。
2. 让报修、回复、状态变化和费用分摊都有时间记录，可追踪责任与结果。
3. 使用清晰的权限边界，防止用户看到不属于其房屋或租约的数据。
4. 从开发初期建立自动化测试和持续集成。
5. 支持部署到 Azure，并将业务核心与 UI、数据库和云服务解耦。

### 2.2 MVP 暂不包含

- 公开房源发布、找房搜索和租赁申请流程；
- 直接代收房租或水电费；
- 银行卡、支付网关和自动转账；
- 具有法律效力的电子签约；
- 信用调查或背景调查；
- 自动读取智能电表；
- 公共房源交易市场的完整竞价流程；
- 会计、税务或法律结论。

MVP 可以记录“谁已支付给谁”，但这只是协作记录，不等同于平台实际处理资金。

## 3. 用户角色

一个账号可以同时拥有多个业务身份。例如，一个用户可以在自己的房产中是房东，在另一套房屋中是租户。

| 角色 | 主要能力 |
|---|---|
| 房东（Landlord） | 管理自己的房产、租约、成员、报修和房屋级沟通 |
| 租户（Tenant） | 查看自己的租约、提交报修、参与沟通、查看和确认共享账单 |
| 室友（Roommate） | 本质上也是某个租约中的租户成员，而不是独立的系统角色 |
| 物业经理（Property Manager） | 代表房东处理指定房产；是否进入 MVP 待确认 |
| 系统管理员（Administrator） | 处理平台运维和滥用问题；不得默认浏览用户私人内容 |

角色权限必须建立在具体资源关系上。“是房东”不代表可以查看所有房屋，“是租户”也不代表可以查看其他租约。

## 4. 核心业务概念

### 4.1 账号与个人资料

- `ApplicationUser`：ASP.NET Core Identity 的技术账号，负责登录、密码、邮箱确认和安全令牌。
- `UserProfile`：业务资料，例如显示名称、头像、联系电话和通知偏好。
- Core 不直接依赖 ASP.NET Core Identity 类型；Identity 属于基础设施边界。

### 4.2 房产与出租单元

- `Property`：房东拥有或管理的房产地址。
- `RentalUnit`：可出租单元。独立住宅可以只有一个单元，公寓楼可以包含多个单元。
- `Listing`：某个单元在特定时间的出租信息。Listing 与已经生效的租住关系不是同一概念。

### 4.3 租约与住户组

- `Tenancy`：某个出租单元在一段时间内的租住关系。
- `TenancyMember`：参与该租住关系的用户，包括加入日期、离开日期和成员状态。
- `TenancyInvitation`：房东或有权限的成员邀请室友加入的记录。

只有处于有效成员期内的用户，才能访问该租约的共享内容。成员离开后默认保留其对本人历史记录的只读访问，但不能看到离开后新增的内容；该规则需要在正式实现前确认。

## 5. 报修业务设计

### 5.1 报修内容

`MaintenanceRequest` 至少包含：

- 所属房产、出租单元和租约；
- 标题、详细描述和问题类别；
- 紧急程度；
- 创建人和创建时间；
- 当前状态；
- 图片或附件；
- 可见范围；
- 指派人、预约时间和解决说明（可选）。

建议的问题类别包括：水管、电气、供暖/制冷、门锁与安全、家电、结构、虫害、网络及其他。

### 5.2 可见性

MVP 默认规则：

- 普通报修默认对当前租约的所有有效成员、房东和被授权的物业经理可见；
- 所有可见成员都可以查看状态和共享讨论，因此室友能够知道房屋正在维修什么；
- 报修人可以把涉及个人隐私或安全的信息标记为“仅房东/管理方可见”；
- 私密报修不得在共享通知、共享账单或室友时间线中泄露标题和内容；
- 平台管理员不能仅凭管理员身份读取报修内容，除非有明确的支持或安全处理流程并留下审计记录。

### 5.3 状态流转

```text
Submitted（已提交）
    ↓
Acknowledged（房东已确认）
    ↓
Scheduled（已预约）
    ↓
InProgress（处理中）
    ↓
Resolved（房东标记已解决）
    ↓
Closed（租户确认关闭）
```

补充流转：

- `Submitted` 可以由创建人在房东处理前取消；
- `Resolved` 可以由有权查看的租户重新打开并说明原因；
- 紧急报修不能只依赖站内消息，界面必须提示用户在危及人身或财产安全时联系当地紧急服务；
- 每次状态变化都记录操作者、时间、原状态、新状态和说明。

### 5.4 报修沟通

每个报修包含独立的消息线程：

- 消息不能静默覆盖；需要修改时保留编辑标识或历史；
- 删除应优先使用软删除并保留审计信息；
- 参与者只收到自己有权查看的通知；
- 附件存储在对象存储中，数据库只保留元数据和受保护的引用；
- 报修关闭后保留只读历史，重新打开后可以继续讨论。

## 6. 房东联系与消息设计

沟通需要附着在业务上下文中，而不是只有一个无法追踪来源的聊天列表。

建议支持：

1. 租约共享会话：当前室友和房东均可见，适合公共事务；
2. 报修会话：只围绕某一报修；
3. 私人会话：租户与房东之间的私密事项；
4. 系统通知：状态变化、邀请、账单发布和到期提醒，不允许用户回复。

共享会话中新增或移除成员时必须明确提示可见范围。新加入的室友能否查看加入前的共享历史，属于待确认的产品决定。

## 7. 水电费及共享账单设计

### 7.1 账单概念

`SharedBill` 表示一张需要在租约成员间分摊的账单，例如：

- 水费；
- 电费；
- 燃气费；
- 网络费；
- 公共清洁费；
- 经成员同意的其他共享费用。

账单至少包含账单类型、账期、总金额、币种、到期日、付款人、凭证附件、分摊规则和各成员份额。

### 7.2 支持的分摊方式

MVP 建议支持：

| 分摊方式 | 规则 |
|---|---|
| 平均分摊 | 总额除以参与人数 |
| 固定金额 | 为每位成员指定金额，合计必须等于总额 |
| 百分比分摊 | 每人百分比合计必须为 100% |
| 按入住天数 | 按账期内每位成员的有效入住天数比例计算 |
| 自定义份额 | 创建者输入分配结果，系统验证合计 |

金额计算规则：

- 使用 `decimal`，禁止使用浮点数；
- 每个金额保留币种所需的小数位；
- 四舍五入产生的最小差额必须按确定性规则分配，并留下说明；
- 所有成员份额相加必须严格等于账单总额；
- 已发布账单不能直接修改金额。需要变更时创建修订版或作废后重建；
- 房租与共享水电账单是不同概念，避免混入同一个计算模型。

### 7.3 账单状态

```text
Draft → Published → PartiallySettled → Settled
                 ↘ Disputed
Draft/Published → Void（满足权限和审计要求时）
```

- `Draft`：只有创建者可见，可以编辑；
- `Published`：参与分摊的成员可见，份额已冻结；
- `Disputed`：成员对账单或份额提出异议；
- `PartiallySettled`：部分成员已记录结清；
- `Settled`：全部份额已记录结清；
- `Void`：账单无效，但历史记录不删除。

### 7.4 付款记录边界

MVP 只记录线下结算：

- 谁应支付；
- 应支付多少；
- 向谁支付；
- 付款人标记已支付的时间；
- 收款人确认收到的时间；
- 可选的付款凭证。

“付款人标记已支付”不能直接等于“已结清”，除非收款人确认，或者产品明确采用单方确认规则。

## 8. 权限矩阵

| 操作 | 房东/授权管理方 | 当前租户成员 | 已离开成员 | 无关用户 |
|---|---:|---:|---:|---:|
| 查看房产基本信息 | 是 | 限租住相关信息 | 历史只读，待确认 | 否 |
| 管理租约成员 | 是 | 仅邀请能力待确认 | 否 | 否 |
| 创建报修 | 是 | 是 | 否 | 否 |
| 查看共享报修 | 是 | 是 | 仅本人有效期内历史 | 否 |
| 查看私密报修 | 是 | 仅创建人 | 仅创建人历史 | 否 |
| 更新报修处理状态 | 是 | 仅确认、重开或取消等有限操作 | 否 | 否 |
| 创建共享账单 | 是，若参与租约 | 是，待产品规则限制 | 否 | 否 |
| 查看共享账单 | 是，若有业务关系 | 仅参与分摊者 | 本人历史 | 否 |
| 确认本人付款 | 若为付款方/收款方 | 若为付款方/收款方 | 历史确认 | 否 |

所有授权必须在服务端根据当前登录用户和目标资源重新检查，不能相信浏览器传入的用户 ID、房东标志或金额计算结果。

## 9. 概念数据模型

以下是概念关系，不代表最终数据库字段已经冻结：

```text
ApplicationUser 1──1 UserProfile

UserProfile 1──* PropertyOwner *──1 Property
Property    1──* RentalUnit
RentalUnit  1──* Listing
RentalUnit  1──* Tenancy
Tenancy     1──* TenancyMember *──1 UserProfile

Tenancy     1──* MaintenanceRequest
MaintenanceRequest 1──* MaintenanceMessage
MaintenanceRequest 1──* MaintenanceStatusHistory
MaintenanceRequest 1──* Attachment

Tenancy     1──* Conversation
Conversation 1──* ConversationParticipant
Conversation 1──* Message

Tenancy     1──* SharedBill
SharedBill  1──* BillShare *──1 TenancyMember
BillShare   1──* SettlementRecord
SharedBill  1──* Attachment
```

建议所有主要业务记录包含：

- 唯一标识；
- 创建时间和创建人；
- 最后更新时间；
- 并发控制字段；
- 必要时包含软删除或归档信息。

时间统一以 UTC 存储，在界面按用户时区显示。金额必须同时保存数值和币种。

## 10. 代码架构

### 10.1 项目职责

```text
RentConnect
├── RentConnect                 Blazor UI、Identity 页面、组合根
├── RentConnect.Core            业务实体、值对象、规则和抽象接口
├── RentConnect.Infrastructure  EF Core、SQL Server、文件、邮件和接口实现
├── RentConnect.UnitTests       纯业务规则的快速测试
└── RentConnect.IntegrationTests 数据库、Identity 和跨层集成测试
```

### 10.2 依赖方向

```text
RentConnect.Core → 不依赖其他项目
RentConnect.Infrastructure → RentConnect.Core
RentConnect → RentConnect.Core + RentConnect.Infrastructure
RentConnect.UnitTests → RentConnect.Core
RentConnect.IntegrationTests → 被测试项目
```

Core 中不引用 Blazor、Entity Framework Core、SQL Server 或 Azure SDK。

### 10.3 模型归属

- Domain Entity、Value Object、业务枚举和业务规则放入 Core；
- `DbContext`、EF 映射、Migration 和 Repository 实现放入 Infrastructure；
- 页面表单、展示模型和 UI 状态放入 Blazor 项目；
- 外部服务返回的数据使用专门 DTO，不直接污染 Domain Entity。

## 11. 测试策略

### 11.1 单元测试

优先覆盖复杂且不依赖数据库的规则：

- 平均、百分比、按入住天数和自定义账单分摊；
- 金额舍入后总和仍等于账单总额；
- 无效状态跳转被拒绝；
- 非成员不能参与租约操作；
- 已发布账单不能被静默修改；
- 报修关闭、重开和取消规则；
- 私密报修可见性规则。

### 11.2 集成测试

- EF Core 映射和 Migration 能在真实 SQL Server 环境运行；
- Identity 注册、确认、登录和授权；
- Repository 查询不会跨租约泄露数据；
- 并发更新报修或账单时能检测冲突；
- 附件和通知的基础设施适配器行为。

集成测试不能只使用 EF InMemory 替代 SQL Server，因为两者的约束、事务和查询行为不同。CI 中建议使用 SQL Server 容器或临时测试数据库。

### 11.3 UI/端到端测试

在核心流程稳定后加入少量高价值测试：注册登录、加入租约、提交报修、室友查看报修、发布账单和确认结算。

## 12. 云端部署方向

建议的 Azure 映射：

| 能力 | Azure 资源方向 |
|---|---|
| Blazor Web App | Azure App Service 或 Azure Container Apps |
| 关系数据库 | Azure SQL Database |
| 报修图片和账单附件 | Azure Blob Storage |
| 密钥 | Azure Key Vault + Managed Identity |
| 邮件 | Azure Communication Services Email 或经评估的邮件服务 |
| 日志与追踪 | Application Insights |
| CI/CD | GitHub Actions |

本地开发使用 LocalDB；生产环境使用 Azure SQL。连接字符串和密钥不能提交到 Git，应使用 User Secrets、环境变量和 Key Vault。

## 13. 安全、隐私与审计

- 对每个查询和命令执行资源级授权；
- 不在 URL、日志或错误页面泄露敏感数据；
- 附件需要类型、大小和恶意内容检查；
- 下载附件使用授权检查和短期访问机制；
- 密码只由 Identity 管理，不进入业务模型或日志；
- 关键事件保留审计记录：成员变化、报修状态、账单发布/作废、份额变化和付款确认；
- 用户生成内容需要防止 XSS、恶意文件和越权引用；
- 开发、测试和生产数据库完全隔离；
- 备份、保留期限、账号删除和数据导出规则需根据目标市场法律进一步确定。

## 14. MVP 建议迭代顺序

### 阶段 1：工程基础

- 完成 Core、Infrastructure、UnitTests 和 IntegrationTests 分层；
- 处理 NuGet 安全警告；
- 初始化 Git 和 GitHub Actions；
- 建立本地与 CI 的测试基线。

### 阶段 2：房产与租住关系

- UserProfile、Property、RentalUnit；
- Tenancy、TenancyMember 和邀请流程；
- 完成资源级授权基础。

### 阶段 3：报修协作

- 创建、查看和更新报修；
- 室友共享可见性和私密报修；
- 状态历史、消息和通知；
- 图片附件。

### 阶段 4：共享账单

- 创建账单和凭证；
- 多种分摊算法；
- 争议、付款申报和收款确认；
- 账单历史和审计。

### 阶段 5：云端上线准备

- Azure 资源和安全配置；
- 生产邮件服务；
- 监控、备份、数据保护和部署流水线；
- 端到端测试和发布检查。

## 15. MVP 验收场景

1. 房东创建出租单元和租约，并邀请两位租户加入。
2. 租户 A 提交共享报修；租户 B 和房东均能看到并收到通知。
3. 房东更新预约和处理状态，所有有权参与者看到一致的历史记录。
4. 租户 A 提交私密报修；租户 B 无法看到其存在或内容。
5. 室友上传一张电费账单，并选择平均分摊。
6. 系统计算的各成员份额总和严格等于账单总额。
7. 一位成员提出争议后，账单不会被误显示为完全结清。
8. 非租约成员即使猜到 URL 或记录 ID，也无法读取报修、消息或账单。
9. 离开租约的成员不能访问离开后产生的新共享内容。
10. 所有关键状态变化均能查到操作者和时间。

## 16. 待确认的产品问题

在创建正式业务模型前，需要逐步确认：

1. 首个目标国家/地区、默认币种和适用法律环境是什么？
2. MVP 是否需要公开房源发布和租户申请，还是先聚焦签约后的租住管理？
3. 一个租约能否包含多个独立房间和不同租金？
4. 室友是否可以邀请新成员，还是只能由房东邀请？
5. 新加入的室友能否读取加入之前的共享消息、报修和账单？
6. 离开的成员可以保留哪些历史访问权限，保留多久？
7. 谁可以创建共享账单：任意当前成员，还是指定的账单管理员？
8. 账单结清是否必须由收款人确认？
9. 是否需要支持房东代付后向租户分摊费用？
10. 报修的私密模式是否允许房东转交给维修人员，以及需要展示哪些信息？
11. MVP 是否包含物业经理角色？
12. 是否需要站内实时聊天，还是线程式留言和邮件通知已经足够？
